# fn-1-homeplane-walking-skeleton-install Homeplane walking skeleton: install → enrol → vault → GNO → harnesses → connector → reversible write → revoke

## Goal & Context
<!-- scope: business -->

Homeplane is a self-hosted, plug-and-play capability plane for Daniel's personal AI agents: one bundle installed on a Mac or Linux machine enrols it with Daniel's server over Tailnet; remote-service credentials and OAuth sessions live only on the server; capabilities (server-side connectors and a locally supervised GNO instance against the Daniel-OS vault) are exposed to agent harnesses through MCP with separately revocable access per machine and harness.

**Product boundary (Daniel, 2026-08-13):** Homeplane is Daniel's self-hosted, portable **personal data and skill layer** for AI agents — three capability families: (1) Daniel-OS + GNO (find/retrieve vault, keep it synchronized, supervise GNO with a disposable per-machine index — vault files sync, GNO indexes never do), (2) personal-data connectors (target set: Google Workspace incl. Gmail/Calendar/Drive/Docs/Sheets/Contacts with authorized writes, Rize, Oura separately grantable, TickTick — Google Drive is only the first acceptance connector, not the scope), and (3) vault-authored skills provisioned into each harness by linking, never by independent editable copies. Homeplane is for Daniel's private life-data layer: technical services clients can install or authenticate locally (GitHub, git, Vercel, shell, filesystem, web search) do NOT pass through it, and it must not grow into a general-purpose agent tool platform. Homeplane distributes access and instructions, not initiative — ordinary clients never inherit scheduled/proactive workflows; one designated operating agent owns recurring jobs and monitoring.

This spec is the smallest end-to-end **walking skeleton** — the thinnest slice that exercises every architectural layer once:

install → enrol → find/retrieve vault → start sync → launch GNO → provision appropriate vault skills → configure Claude Code and Codex → access GNO, Google Drive (read-only) and Google Calendar → create/read/update/verify/delete an isolated test calendar event → revoke one harness without affecting the other.

Its purpose is to force the real integration risks (enrolment identity, credential custody boundary, vault retrieval + sync, GNO supervision, skills provisioning, harness config, MCP exposure, revocation) into one working path before any layer is deepened. Target user: Daniel, on a fresh Mac or Linux machine.

## Architecture & Data Models
<!-- scope: technical -->

Two planes:

**Server (already exists as Daniel's Tailnet server):**
- `homeplane-server` — the control plane. Owns: enrolment registry, grant/credential registry, audit log, and the server-side connector runtime.
- Connector runtime: **compose an existing OSS MCP gateway/runtime — ToolHive is the leading candidate** — rather than building one. Homeplane wraps it with enrolment-scoped access issuance and revocation; it does not reimplement MCP proxying, secrets storage, or container supervision that the composed component already provides.
- Credential custody: provider OAuth sessions and API keys exist **only** here (in the composed component's secret store or an equivalent server-local store — open decision D3). The store must make adding OAuth credentials easy: a client-initiated `add-credentials` flow (R13, D10) completes the provider OAuth dance in cooperation with the server and lands the credential server-side, immediately usable by every enrolled client.
- Connector manifest: connectors are registered declaratively — {provider, required credential ref, MCP server/tools source, and a **per-tool mapping to action class (read|write|send|delete) and required capability**}. The edge enforces grants' capability sets and derives audit action class from this mapping declaratively — no connector-specific authorization code. Each entry also carries **credential-acquisition metadata**: a reference to a standard credential driver (skeleton ships one: `oauth2-authcode`) plus its declarative parameters (auth/token endpoints, scopes, client-id/secret refs). **Bootstrap of provider app credentials (e.g. the Google OAuth client id/secret) is a server-local import** — `homeplane-server admin secret import <ref>` reading from protected stdin or a validated 0600 file into the D3 store; app credentials never ride the network API — so onboarding a second provider is a manifest entry + `add-credentials`, with zero changes to enrolment, broker, edge, or harness code (R12's real test). Each tool mapping MAY also declare a **declarative artifact-id extractor** (a JSONPath-style pointer into the tool's request or response); when present the audit row records that artifact identity, when absent it records the tool name plus a digest (hash) of the request arguments — never the arguments themselves — and artifact_id `unknown`. **Unmapped tools fail closed:** a tool exposed by the gateway with no manifest mapping is denied at invocation time and the denial audited as a policy violation — a connector upgrade can never introduce an unclassified write/send/delete tool with implicit access; registration is refused where the tool list is known and incomplete. This keeps audit generic across arbitrary MCP tools without connector-specific code or payload logging; the Calendar tools used by R8 declare extractors (event id), and the Drive read tools declare extractors (file id) (per D18: Drive is read-only, its write tools stay unmapped). The manifest is **connector-agnostic** — Google Drive (read-only) + Calendar (read/write) are only the first entries (acceptance-test connectors, D5/D18); adding entries never changes the enrolment/identity/custody/authorization/audit/revocation/harness-config architecture (R12).

**Machine (each enrolled Mac/Linux box):**
- `homeplane-agent` — installed by the one-bundle installer. Responsibilities in the skeleton:
  1. **Enrolment:** reach the server over Tailnet, present an operator-approved join (open decision D2), receive a machine identity; request per-harness grants from the server.
  2. **Vault:** detect an existing Daniel-OS Obsidian vault; if absent, retrieve it via Obsidian Sync (D4) and record its directory in agent config; keep it **continuously synchronized** thereafter (sync is supervised like any other agent responsibility and reported in `status`).
  3. **GNO:** install, configure, launch, and supervise GNO against that vault (launchd on macOS, systemd user unit on Linux). GNO maintains a **disposable, per-machine local index** (never synced, rebuildable from the vault at any time). GNO search/retrieval/controlled-writes are exposed to harnesses as a local MCP server.
  4. **Harness config:** detect installed harnesses and write MCP-server entries (local GNO + server connector endpoint with that harness's own credential) into each harness's config **without overwriting unrelated settings** (read-modify-write, merge-only, backup before write).
  5. **Skills provisioning:** discover Daniel-authored skills in the vault (the canonical source), assign them per profile, and link them into each harness — native external skill directories or symlinks where the harness supports them, thin generated target-native adapters otherwise; **never independent editable copies**. Refresh links after vault/skill changes; verify discovery in a fresh harness process; mark harness-specific or incompatible skills as unsupported rather than pretending portability. Skills may contain procedures, references, templates, and safe scripts — never credentials or runtime state.

**Identity & grant model (skeleton-minimal):**
- `Machine` — enrolled device; keyed by Tailnet node + enrolment record.
- `Grant` — (machine, harness) → capability set; carries its own revocable secret/token. Two harnesses on one machine hold two distinct grants; revoking one leaves the other valid. Granularity is deliberately machine+harness only (Daniel, 2026-08-13: no workload-level grants).
- `AuditEvent` — append-only record on the server of **every connector tool call** (action class: read/write/send/delete, outcome, artifact identity) plus enrolment/grant lifecycle events. **Attribution splits observed vs authenticated identity, with an explicit actor model** (`actor_kind = machine | operator | system`): network calls record the WhoIs-derived source machine (observed); server-local admin CLI events record a local-operator actor (no observed machine — there is no network caller); system events (expiry, supersession) record `system`; authenticated rows additionally record (harness, grant); rejected calls (invalid token, replayed token, unmapped tool, revoked grant) record a safe presented-token fingerprint + violation reason instead — never misattributed to the token's owner, never dropped. **Audit stores metadata, never payload bodies by default** (no document contents, email bodies, or note text in the log). Skeleton records: enrolment, grant issuance/revocation, and all six steps of the reversible-write proof including the read-back/verify calls.

**Data flow for the skeleton's proof calls:** harness → local GNO MCP (vault read) and harness → server connector MCP endpoint over Tailnet (per-harness token) → composed gateway → provider. **The connector edge binds tokens to machines:** every connector call verifies the bearer token AND that the WhoIs-resolved source tailnet node matches the grant's machine — a token replayed from another machine is rejected and audited as a violation, not attributed to the original machine. The reversible write goes through the server-side connector and is audited.

## API Contracts
<!-- scope: technical -->

Skeleton-level contracts (transport details finalized during implementation; shapes are the contract):

- `POST /enrol` (server, Tailnet-only): request `{machine_name, os}` → response `{machine_id, machine_credential}`. Enrolment is auto-approved for tailnet nodes (D12 — no pending state in the skeleton; an approval queue is deferred until non-owned machines exist). The server stores only a credential hash, so **re-enrol is explicit rotation, not a silent no-op**: the same machine record is kept (no duplicate identity), a NEW machine_credential is returned, and the old one is atomically invalidated — the agent persists the new credential before acknowledging. Errors: unreachable server → clear message + retry guidance, no partial local state.
- `POST /grants` (server, machine-credential auth): request `{harness, capabilities}` → response `{grant_id, endpoint_url, grant_token}`. **Authorization invariants:** the WhoIs-resolved tailnet node must match the enrolled machine identity, the presented machine credential must hash-match that machine's record, and the grant is created for the calling machine only (no caller-supplied machine_id). **Capabilities are server-policy-bound:** the server holds a per-harness capability policy (what each known harness may be granted); a request for capabilities outside policy is clamped or rejected — the client never self-selects its authority. Grants are issued active; issuing a new grant for the same (machine, harness) supersedes and revokes the prior one, and the agent's `configure-harnesses` flow is idempotent — if a config write fails, re-running requests a fresh grant and rewrites the config, converging to a consistent state (two-phase activation and revocation tombstones are deliberate post-skeleton hardening — see Boundaries). Exactly one active grant per (machine, harness). Errors: unknown machine → 401; revoked machine → 403; cross-machine attempt → 403; over-policy capabilities → clamped or 403 (explicit per policy).
- `DELETE /grants/{grant_id}` (server, machine-credential auth): revokes exactly that grant; subsequent MCP calls with its token fail with an auth error. **Authorization:** the grant must belong to the calling machine (or an explicit operator credential); cross-machine revocation → 403. Errors: unknown grant → 404; idempotent on repeat.
- `GET /grants` (server, machine-credential auth): lists the calling machine's grants with non-secret metadata `{grant_id, harness, capabilities, state (active|revoked), revoked_at}`. `homeplane-agent status` reconciles against this — never reports cached grant state as live; server-unreachable is reported as `unknown (server unreachable)`, distinct from `active`. Errors: unknown machine → 401.
- `GET /healthz` (server): reports **server-side components only** (store, gateway/connector runtime, tsnet listener, credential store). `homeplane-agent status` (machine CLI): reports **machine-side state** — enrolment, vault path, sync state, GNO supervision (running/pid/restart count), configured harnesses, skills summary, and grants reconciled live via `GET /grants`. Machine-local failures surface in `status`, never in `/healthz`. Errors: degraded → BOTH a non-2xx status AND an explicit component-level degraded payload (healthz; `curl -sf` must fail) / non-zero exit + named component (status).
- **Operator surface (skeleton): server-local admin CLI**, not HTTP — `homeplane-server admin audit [--since…]`, `homeplane-server admin revoke-grant <id>` run on the server host itself (machine-level revocation and block/unblock tombstones are deferred hardening — see Boundaries); the operator identity is local shell access to the server (single-operator reality; an operator HTTP credential is deferred). Machines never read global audit; cross-machine revocation happens only via this CLI. No error surface beyond command errors.
- `homeplane-agent add-credentials <provider>` (machine CLI) + credential-flow API (server, machine-credential auth). The flow is an explicit asynchronous state machine, not a single request:
  - `POST /credentials/flows` with `{provider, replace: bool, redirect_uri}` → `{flow_id, authorization_url, expires_at}`; flow state starts `pending`. The `redirect_uri` is the client's chosen loopback address (host:port bound by the client before the request); the server VALIDATES it is a genuine loopback form — `http://127.0.0.1:<port>` or `http://[::1]:<port>` only, anything else → 400 — Google requires the authorization URL and the token exchange to use this exact redirect URI, so the server builds the authorization URL with it and uses it again at exchange time.
  - Code relay: the OAuth redirect lands on the client's loopback listener; the client relays the outcome once via `POST /credentials/flows/{flow_id}/code` with `{code, state}` on success or `{error, state}` on provider denial (one-shot: second call → 409; PKCE + state verified server-side).
  - `GET /credentials/flows/{flow_id}` → `{state: pending|completed|denied|expired|failed, provider, created_at, expires_at}` plus, on any terminal failure, a safe diagnostic `{error_code, message, retryable}` (distinguishes provider denial, exchange failure, store failure, expiry, and lost-concurrent-commit; NEVER contains provider response bodies or tokens). The agent polls until terminal. `failed` = provider token-exchange or credential-store failure after a valid code (retryable with a new flow; nothing partial stored).
  - On `completed` the credential is stored server-side and immediately usable by existing grants. **Replacement is an atomic swap:** the existing credential stays active until the replacement is durably stored; every unsuccessful terminal state (`denied`/`expired`/`failed`/abandoned) preserves the old credential untouched. **Concurrent flows are serialized per provider** (or commit via compare-and-swap against the credential generation observed at flow creation): when two flows race, exactly one commits and the loser terminates `failed` with a clear must-retry/replace message — no silent overwrite. Credentials never transit to or persist on the machine.
  - Errors: `denied`/`expired`/`failed`/abandoned → no partial credential stored, clear message; already-configured provider → start refused unless `replace=true` (see R13); unknown provider (not in the connector manifest) → 404 listing known providers.
- MCP surface: harnesses speak standard MCP (stdio for local GNO; HTTP/SSE-or-streamable over Tailnet for server connectors, `Authorization: Bearer <grant_token>`). The connector tool set is whatever the composed gateway exposes per manifest entry — for the skeleton, Google Drive (D5); the full capability set of each configured credential is exposed through the same surface (R13).

## Edge Cases & Constraints

<!-- scope: technical -->

- **Merge-only harness config:** harness config files may contain unrelated MCP servers and settings; writes must be surgical (parse, merge, write back; keep a timestamped backup). A malformed existing config aborts that harness's configuration with a clear message — never clobber.
- **Vault detection ambiguity:** multiple candidate vaults → do not guess silently; skeleton may take an explicit `--vault-path` override. Absent vault + Obsidian Sync retrieval failure → enrolment still succeeds; vault/GNO steps report degraded and retryable.
- **Partial failure ordering:** enrolment succeeds but GNO fails → server connectors still usable; each stage independently reported in `status`.
- **Revocation semantics:** revocation is server-side (token invalidation) — it must not require touching the machine; the revoked harness's *local* GNO access is out of scope for the skeleton (open decision D7 covers extending revocation to local capabilities).
- **Threat-model honesty (same-OS-user limitation):** both harnesses on one machine run as the same OS user, so per-harness token separation on a single machine is an *operational revocation boundary*, not a security boundary against a malicious local process — a process running as Daniel can read the other harness's 0600 token file. What the grant model DOES guarantee: server-side per-harness kill switches (revoke/tombstone), per-harness attribution in audit, machine binding at the edge (a token exfiltrated to another machine is useless), and server-policy-bound capabilities. Cross-user or sandboxed isolation is out of scope for the skeleton and recorded here so nobody mistakes the claim.
- **Gateway bypass boundary:** the composed gateway's upstream listener binds only to loopback (or an isolated namespace) on the server — it must be unreachable from any other tailnet/LAN node; only the Homeplane edge is network-reachable, so grants/revocation/capability checks/audit cannot be bypassed. Verified by a direct-access-fails test from a second node.
- **Security boundaries:** all machine↔server traffic Tailnet-only (no public listener), but tailnet reachability is never sufficient authorization — every capability call requires a valid grant. Grant tokens are per-harness, never shared, never written into a harness config another harness reads. Provider credentials never transit to machines and never appear in repositories, logs, argv, generated configs, or model context. Connector access does not itself authorize a consequential action — sends/deletes remain subject to whatever authorization the grant's capability set encodes.
- **Reversibility constraint:** the proof write must be trivially reversible and actually reversed as part of verification (create-then-delete, or write-then-restore), with both actions audited.
- **Idempotence:** re-running the installer refreshes the install in place; re-running `enrol` on an already-enrolled machine is **identity-preserving credential rotation** (same machine record, new credential, old invalidated) — never a duplicate identity and never a silent no-op.

## Acceptance Criteria
<!-- scope: both -->

- **R1:** A single installable bundle brings `homeplane-agent` onto a fresh macOS (13+, launchd) or supported-Linux (systemd-based distro with `systemctl --user` + linger available — Ubuntu/Debian/Fedora class) machine with one command, from checksummed release-form artifacts; the installer detects and REJECTS unsupported init systems before installing; Node 22 is provisioned deterministically (distro package or vendored tarball) (a locally staged artifact set is acceptable for the skeleton; a published CI release pipeline is deferred — see Boundaries). Errors: unsupported OS → clear message + non-zero exit; checksum mismatch → abort, no partial install; re-run on installed machine → idempotent refresh (install), identity-preserving rotation (enrol).
- **R2:** `homeplane-agent enrol` registers the machine with the server over Tailnet and stores a machine identity; the server records the enrolment. Errors: server unreachable → actionable error, no partial local state; re-enrolment → identity-preserving credential rotation, never a duplicate record.
- **R3:** The agent finds an existing Daniel-OS vault, or retrieves it via Obsidian Sync when absent, and records the vault directory in its config. Errors: retrieval failure → degraded state reported by `status`, retryable; ambiguous multiple vaults → explicit selection required, no silent guess.
- **R4:** The agent installs, configures, and runs GNO against the configured vault, reachable as a local MCP server, with lifecycle semantics matching the D8-resolved mode: **daemon mode** → supervised, survives process death (restart), `status` reports pid + restart count, crash-loop surfaced; **stdio mode** → health-checked launch template, `status` reports last-probe result + per-launch failures (no persistent-pid claim). Errors: crash-loop / repeated launch failure → degraded in `status`; vault missing → GNO not started, degraded state named.
- **R5:** Two distinct detected harnesses (Claude Code and Codex, per D1) are each configured with (a) local GNO MCP and (b) the server connector MCP endpoint using **that harness's own grant token**; unrelated pre-existing configuration in each harness config is **semantically preserved** (parse of the file after the write, minus the Homeplane-managed entries, is deep-equal to the parse before), writes are span-scoped where the format allows (TOML: only the managed table is touched), and a timestamped backup precedes every write. Grant tokens live only in user-scoped files with 0600 permissions and never land in any git-shared file (Claude Code: user/local scope only, never project-scope `.mcp.json`); provider tokens never reach the machine at all (custody rule). Errors: malformed existing config → skip that harness with clear message + backup intact.
- **R6:** From each configured harness, an MCP call to local GNO returns real vault content. Errors: no error surface beyond R4's degraded states.
- **R7:** From each configured harness, MCP calls to the Google connectors succeed via the server — a Drive READ (Drive is read-only by scope policy, D18) and a Calendar read — with the provider credential resident only on the server, verified by inspecting the machine for absence of provider credentials. A Drive write-class tool is either absent from the manifest or denied fail-closed (never authorized). Errors: revoked/invalid grant token → auth error, not a hang.
- **R8:** The reversible-write proof runs through the Google Calendar connector, as a six-step sequence on an isolated, uniquely named test event (summary embeds machine+harness+timestamp; a dedicated Homeplane test calendar is used when the granted scope allows calendar creation, else the event is namespaced in the primary calendar): (1) create the event; (2) read it back; (3) update it; (4) verify the update; (5) delete it; (6) verify cleanup. No pre-existing event is touched at any step. **All six steps — including the read-back and verify calls — appear in the server audit log** with action class and (machine, harness, grant) attribution, metadata only (no payload bodies). Errors: any step failure → stop the sequence, surface the error, and leave a loud pointer to whatever artifact remains (never silently continue).
- **R9:** Revoking one harness's grant immediately (≤ one token-validation interval) causes that harness's server-connector calls to fail with an auth error, while the other harness's calls continue to succeed; the revocation is audited. Errors: revoking an unknown grant → 404; repeat revocation → idempotent.
- **R10:** `homeplane-agent status` reports machine-side state (enrolment, vault, sync, GNO, harness config, skills, live-reconciled grants) and server `/healthz` reports server-side component state — each verified truthful for the failure modes the demo path actually hits (revoked grant, server unreachable, GNO down, vault missing); machine-local failures are status's job, never /healthz's (no error surface beyond accurate reporting + non-zero exit / non-2xx when degraded).
- **R12:** The architecture and connector manifest are connector-agnostic: adding a second connector requires only a new manifest entry plus its credentials — zero changes to the enrolment, identity, credential-custody, authorization, audit, revocation, or harness-configuration architecture. Verified in the skeleton by design review of the manifest/registration path (a second live connector itself is out of scope). Errors: no error surface beyond the design-review check.
- **R13:** A client machine can invoke `homeplane-agent add-credentials <provider>` which runs a secure OAuth flow in cooperation with the server (per the credential-flow state machine in API Contracts) such that the resulting credential is stored only on the server and immediately usable by every enrolled client's grants; the credential defines the maximum provider tool surface exposed via the manifest, while every invocation remains restricted by the calling grant's capability set. Errors: flow abandoned/denied/expired → no partial credential stored, clear message; provider already configured → explicit re-auth/replace confirmation, never silent overwrite; unknown provider → 404 listing known providers.
- **R14:** After setup, the vault remains synchronized (Obsidian Sync running under supervision, pinned CLI version, real vault snapshotted before first activation); vault files sync across machines while the GNO index stays local, disposable, and rebuildable — the index is never written into the vault or any synced path. Errors: sync process failure → degraded state in `status`, retryable, vault remains usable read-locally; sync auth failure distinguished from network failure. (Full conflict-rehearsal matrix deferred — see Boundaries.)
- **R15:** Vault-authored skills baseline: at least one real skill is discovered from the vault, assigned via one profile, and linked into BOTH harnesses (native external skill directory/symlink where supported; thin generated adapter otherwise) with no independent editable copies; a skill visible in a **fresh harness process** proves provisioning; genuinely harness-specific skills are marked unsupported with a reason rather than silently linked. Unrelated harness configuration is preserved (same discipline as R5). Errors: unsupported skill → recorded + surfaced, never silently linked. (Refresh/dangling-link machinery deferred — see Boundaries.)

- `homeplane-agent uninstall` and credential cleanup on removal.
- Full Obsidian-Sync conflict-rehearsal matrix — the pinned version + pre-activation vault snapshot remain; systematic conflict scenarios are deferred.
- Skills refresh/dangling-link repair machinery beyond the R15 baseline.
- Audit metadata-only discipline is retained as a schema property of `AuditEvent` (asserted in .2's tests) rather than a standalone criterion.

## Decision Context
<!-- scope: both — conditionally substructured -->

### Motivation
<!-- scope: business -->

Capability is currently entangled with configuration: every machine × harness pairing costs repeated provider auth and hand-setup, spreads credentials, and offers no revocation or audit. A walking skeleton across all layers, before deepening any of them, is the fastest way to expose the risky integrations (enrolment identity, Obsidian Sync retrieval, GNO supervision, harness config merging, composed-gateway fit) while delivering a genuinely usable first increment.

### Implementation Tradeoffs
<!-- scope: technical -->

- **Compose, don't build:** ToolHive (or equivalent) is preferred over a bespoke MCP gateway — MCP proxying, secret custody, and workload supervision are commodity; Homeplane's value is enrolment, per-grant issuance/revocation, vault/GNO bootstrap, and harness config.
- **Tailnet as the network boundary:** removes public-endpoint hardening from the skeleton entirely; the cost is that everything assumes the tailnet exists and is trusted, which matches the single-operator reality.
- **Server-side-only revocation in the skeleton:** token invalidation is enough to prove per-grant independence (R9) without building a local policy agent.
- **Walking skeleton over vertical depth:** every layer is deliberately minimal (one connector, two harnesses, one write) to keep the slice honest.

**Unresolved decisions (recorded honestly — each must be resolved before or during its task, none silently defaulted):**

- **D1 — Which two harnesses for the skeleton. RESOLVED (Daniel, 2026-08-13): Claude Code + Codex** — both installed on Daniel's machines today, both have well-documented MCP config formats. Other harnesses (Hermes, Cursor, Grok) follow post-skeleton.
- **D2 — Enrolment identity & approval mechanism. RESOLVED (Daniel, 2026-08-13): Tailscale to start** — machine identity comes from Tailscale node identity (tailnet ACLs/grants, identity via `tsnet`/serve); Homeplane layers per-harness grants with their own revocable tokens on top, since Tailscale only identifies machines.
