## Goal & context

Add **grok** (xAI's `grok` CLI) as Homeplane's third supported harness, proving the walking skeleton's central architectural claim: adding a harness touches only detection, config writing, and skills linking — enrolment, identity, credential custody, policy resolution, audit, and revocation need zero changes. The one permitted server-side touch is registering the harness name in the policy table ([policy.go:39-79](internal/policy/policy.go)).

After fn-1, this machine has Claude Code and Codex fully wired: each holds its own machine-bound grant, reaches the Google connector through the server edge on clawniel, reaches local GNO over stdio, and has vault-authored skills linked natively. The grok CLI is installed (`~/.grok/` exists) but Homeplane does not detect or configure it.

Verified surfaces (probed live on this machine): `grok mcp add <name> <url> -t http -H "Authorization: Bearer <token>"` (streamable HTTP + bearer header, same shape as Claude Code) plus stdio transport; management verbs `list/add/remove/enable/disable/doctor`. `~/.grok/skills/` exists (empty) — discovery convention unverified. `~/.grok/config.toml` exists; whether MCP entries live there or in a separate CLI-managed store is unverified.

Repo seams (from repo-scout, all verified): `harness.Known()` + consts (harness.go:45-51), `Locator`/`Detect()` (detect.go:36-161), `writerFor()` (configure.go:276-285) with `tomledit.go` byte-span precedent, `connectorEntry()` bearer-header shape (configure.go:292-299), format-agnostic backup/restore and `assertUserScope`, `skills.Known()` + `SkillsDir()` (link.go:48-79) — **two separate `Known()` registries that must update in lockstep**, `UnsupportedSkill` marking (profile.go:79-108), `policy.Default()` (policy.go:71-79), e2e stage list (test/e2e/run.sh:11-14), data-driven status/grants surfaces.

Scope guardrails from fn-1 carry over verbatim: tokens never in repos/logs/argv/model context (containment = resolve symlinks + `git check-ignore`, never file mode alone — memory `bug/security/0600-and-a-filename-check-are-not`); semantic-preserving merges only; skills linked, never copied; mint authority last (validate every local step before requesting a grant); per-harness grant separately revocable; tailnet reachability is never authorization.

## Acceptance criteria

- **R1:** `homeplane-agent configure-harnesses -detect` (the existing read-only detection mode; no new subcommand) detects grok when the grok CLI is present, reports it alongside claude-code and codex, and reports "not detected" cleanly on machines without it. Error/boundary cases: grok installed but never launched (missing or minimal `~/.grok` state) must yield a definite detect verdict, not a crash; a grok binary whose `mcp` subcommand is absent (version drift) is reported as detected-but-unsupported with the observed version in both the machine-readable and human output (the detection model carries observed version + a supported verdict, and unsupported gates BEFORE any grant issuance); a relocated config home (GROK_HOME-equivalent env var, if the probe finds one) is honored like `CODEX_HOME`.
- **R2:** The existing configure entrypoint wires grok with its OWN policy-bound grant: gno stdio MCP entry + Homeplane edge HTTP entry with bearer auth, written by the mechanism task .1's probe ratifies (CLI verbs or byte-span merge), with pre-existing grok MCP entries and unrelated settings preserved (proven against a seeded non-empty config); token destination passes the git-containment test (resolved symlinks + `git check-ignore`), 0600, never in argv or logs; every touched file backed up and restorable; re-run converges idempotently; grant minted only after all local validation succeeds — NOTE the current `configureOne` order is NOT mint-authority-last (IssueGrant at configure.go:206 precedes Writer.Apply's containment/parse/backup/preservation checks at writer.go:81-205); .2 restructures this into a two-phase writer transaction: preflight (containment, entry validation, parse/renderability, preservation dry-merge, backup + writability, state-record validation) BEFORE IssueGrant for EVERY harness, with only token/endpoint substitution and the race-checked atomic commit after issuance, under the existing state lock, with tests proving the issuer is never called when any local precondition fails. Error cases: a failing config write rolls back via backup and records a distinct harness outcome; partial success (one of two entries written) leaves a defined state the next run repairs.
- **R3:** From a fresh grok process (leader-process semantics per task .1's probe — the proof must defeat a stale resident process, not coincide with it), an MCP call to local GNO returns real vault content, and calls through the server edge perform a real Drive read AND one guarded `manage_event` op with `send_updates:"none"` — audited server-side under grok's grant identity with correct action class and a real artifact ID (never "unknown").
- **R4:** At least one vault-authored skill from the active profile is linked into grok's skills surface and discovered by a fresh grok process; the profile schema (schema 1) supports grok as a third harness key with absence-is-safe defaults; unknown harness keys STAY fail-closed (the profile.go:209-215 reject is correct — warn-and-skip would fail open on typos like `[harness.codxe]`; the typo-rejection test is retained); the ACTIVE vault file edit (adding the grok assignment) is an explicit .3 step with evidence, preserving existing assignments byte-for-byte and gated on a rollout check: every machine consuming the synced profile runs a grok-aware agent (verified against the server's enrolled-machine list — today exactly this one machine — and recorded in evidence; if fleet-wide upgrade cannot be verified, the literal grok key is deferred and defaults apply until it can); a skill grok's convention cannot host natively is marked `unsupported` via the existing mechanism, never adapted silently. The fresh-process discovery check runs through the PRODUCT path (`skills provision -verify` → Verifier.Discover("grok") in internal/agent/skills/verify.go, extended in .2 with the .1-ratified leader/fresh-process contract), not a bespoke e2e probe; linked-but-not-discovered is a recorded failure state distinct from unsupported, and verifier tests cover success, timeout, linked-but-not-discovered, and unsupported-without-probe.
- **R5:** Revoking grok's grant via the operator CLI cuts grok's connector access within one token-validation interval while Claude Code and Codex calls keep succeeding — and the inverse: revoking Claude Code's grant leaves grok working. Both directions proven live, audited, grants restored afterwards. The proof PRODUCES each failure (a real denied call), never asserts on shape alone.
- **R6:** `homeplane-agent status` truthfully includes grok via an explicit detection/support model (observed version + supported verdict + reason) reconciled with configuration records AND live grants — the five states not-detected / detected-unconfigured / detected-unsupported / configured / revoked each render distinctly (the current status.go:478-504 derives only from the persisted configured list, so this is new modeling work in .2, not a verify-only step), and a machine-readable evidence file records every R-ID's proof at the shipped commit, gated by an fn-3 acceptance gate following fn-1's pattern (versioned evidence, commit-matched, artifact identities non-"unknown", ratified-limitations table, demonstrated rejection of tampered evidence).

## Boundaries / non-goals

- **The R12 falsification gate:** if grok support requires ANY change to enrolment, grant issuance/validation, credential custody, policy *resolution*, audit, or the edge, that is a finding to surface — it falsifies fn-1's harness-agnostic claim — not something to quietly implement. The policy-table entry (`HarnessGrok` const + `Default()` row with the same capability set as the other two) is the one permitted touch.
- Hermes and Cursor remain post-skeleton; no harness auto-discovery framework — grok follows the same explicit-probe pattern.
- No grok-specific skill adapters: native directory linking or honest `unsupported` marking only.
- D8 (gno daemon-vs-stdio) stays open — grok gets the stdio arrangement the machine currently runs; this spec must not change the gno lifecycle mode.
- Obsidian sync arrangement unchanged (detect-only; Obsidian.app is the sync client).
- Google scopes unchanged (D18); no new connector; no new consent (credential already brokered).
- grok's own model/auth configuration (xAI account, API keys) is out of scope — only the `mcp` and `skills` surfaces.
- Deconfigure/uninstall of grok's Homeplane-managed entries: deferred with the fn-1 uninstall deferral (same revisit trigger); not an R-ID.
- fn-1's `scripts/final-gate.py` and e2e assertions stay untouched as fn-1's historical record where they say "both harnesses"; fn-3 extends stages and adds its own gate.
- `grok mcp doctor` as a rich status signal: use it in the .1 probe and (if cheap) in configure verification; not a standing status dependency.

## Decision context

- **D1 (fn-3) — grok's skills discovery convention: OPEN, resolved by task .1.** Directory name (like Claude Code) vs frontmatter name (like Codex), symlink support, and whether discovery requires a restart — pinned by probing a disposable skill in a fresh process (contract-capture pattern: `scripts/capture-gno-contract.sh` is the exemplar; never invent a CLI surface). Determines whether `RuleNameMismatch` logic applies.
- **D2 (fn-3) — config write mechanism: OPEN, resolved by task .1.** `grok mcp add/remove` CLI verbs vs direct byte-span edit of the real config store. The probe must answer: where entries actually live (config.toml vs separate store; `grok mcp list` is the authoritative read), whether `add` is idempotent or clobbers/duplicates, whether it preserves unrelated entries byte-for-byte, whether entries can land disabled (and whether `enable` is needed), what a non-interactive failure looks like (no hangs — any CLI-verb writer needs a timeout), and how backup/restore composes (if CLI verbs touch state beyond the file, raw-byte restore is insufficient — record what "restorable" means). If direct file editing is ratified, fn-1's `tomledit.go` byte-span discipline applies; if CLI verbs, the writer is a new pattern and `Configurator`'s backup/outcome recording must be extended deliberately, not coincidentally.
- **D3 (fn-3) — token custody shape: follow the probe.** Prefer env-var indirection if grok supports it (Codex `bearer_token_env_var` precedent); a 0600 config-file bearer matches the Claude Code precedent and is acceptable — either way the destination passes the git-containment test and never appears in argv (`grok mcp add -H "Authorization: Bearer <token>"` puts the token IN ARGV — if CLI verbs are the only write path, the token must reach the config another way, e.g. write-then-edit or env indirection; this is a hard constraint on D2's resolution).
- **Leader process:** `~/.grok/leader.sock` exists — task .1 probes whether a resident leader serves MCP config stale and how to force a genuinely fresh process for R3/R4 proofs.
- Model routing per project pins: fable-5 conducts, opus-5 workers, gpt-5.6-sol reviews via codex bridge (xhigh). Live proof on this machine against clawniel; guarded Calendar ops reversible; no artifacts left behind.
